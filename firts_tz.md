# Техническое задание

## Everty MultiLink — интеллектуальный мультисерверный VLESS-клиент

ТЗ · Версия 0.1 · Windows

Идея: разработать приложение, которое позволяет использовать множество VLESS-серверов из одной или нескольких подписок одновременно, автоматически распределять подключения, выбирать оптимальные маршруты и обеспечивать устойчивую работу интернета при отказах отдельных серверов.

Это должен быть не очередной VPN-клиент с кнопкой выбора страны, а интеллектуальный менеджер сетевых маршрутов, который самостоятельно управляет доступными прокси-серверами.

Технологический стек: Rust + EvertyUI, сетевой движок Mihomo, Windows 10/11. Архитектура должна предусматривать последующую поддержку Linux и macOS.

Разделение ответственности:

- EvertyUI отвечает только за интерфейс.
- Rust Orchestrator управляет подписками, политиками, жизненным циклом процессов и состоянием.
- Mihomo реализует сетевые протоколы и маршрутизацию.
- Локальное хранилище сохраняет конфигурации, историю измерений и настройки.

Приложение не должно запускать отдельную копию Mihomo для каждого сервера. Один экземпляр ядра способен управлять множеством прокси-узлов и группами балансировки.

Smart Balance

Автоматически выбирает доступный пул и распределяет новые соединения между серверами. При ухудшении качества узел временно исключается.

Алгоритм: Health checks + динамический пул + load-balance

### Особенности Smart Balance

Это основная функция, которая отличает Everty MultiLink от простого конфигуратора.

- Учитывать доступность, задержку, ошибки подключения и историю работы.
- Не переключать маршрут из-за одного неудачного измерения.
- Исключать неисправные серверы после нескольких последовательных ошибок.
- Возвращать сервер после успешных проверок с периодом восстановления.
- Не разрывать исправные активные соединения ради перераспределения.
- Использовать гистерезис, чтобы не происходили постоянные переключения между почти одинаковыми узлами.

Важно: Mihomo поддерживает штатные группы `load-balance`, `url-test` и `fallback`.&#x20;

## 5. Менеджер подписок

Пользователь вставляет ссылку, например:

`https://provider.example/subscription/secret-token`

Приложение должно:

1. Скачать подписку по HTTPS.
2. Распознать поддерживаемый формат: VLESS URI, Base64-список URI или Mihomo YAML.
3. Извлечь узлы, сохраняя настройки TLS, SNI, REALITY, transport и другие параметры.
4. Проверить конфигурацию и сообщить о неподдерживаемых параметрах.
5. Сохранить серверы в локальной базе.
6. Обновлять подписку по расписанию без потери пользовательских настроек.

Дополнительно: поиск дубликатов по параметрам соединения, фильтрация по стране, имени и задержке, ручное исключение конкретных узлов.

Адреса подписок и идентификаторы доступа считаются секретами, не попадают в обычные журналы, а локально защищаются средствами Windows DPAPI.

## 6. Мониторинг и статистика

| Метрика            | Назначение                            |
| ------------------ | ------------------------------------- |
| RTT                | Задержка до проверочного адреса       |
| Availability       | Успешность проверок доступности       |
| TCP Connect        | Время установки соединения            |
| Download / Upload  | Скорость передаваемого трафика        |

Необходимо различать измеренные значения и расчётные показатели. Например, высокая задержка не доказывает низкую пропускную способность, а число подключений не является загрузкой сервера по CPU.

Для отображения общих соединений и трафика использовать локальный controller API Mihomo, включая `/connections` и `/traffic`.&#x20;

## 7. Системная интеграция Windows

Первая версия реализует два варианта:

System Proxy: изменение пользовательских настроек системного прокси с сохранением исходных значений для восстановления после отключения.

TUN: отдельный режим для маршрутизации IP-трафика приложений, которые не учитывают системные прокси. Потребуются соответствующие права, виртуальный сетевой интерфейс и работа с маршрутами.

Обязательные условия:

- Восстановление настроек после штатного завершения и аварийного сбоя.
- Контроль утечек DNS и IPv6 в соответствии с выбранным режимом.
- Исключение зацикливания собственных соединений приложения.
- Локальный API Mihomo слушает только loopback-интерфейс, с аутентификацией.
- Режим Fail Closed: при потере всех серверов трафик блокируется, если пользователь выбрал защиту от прямого выхода.
- Режим Fail Open: разрешение прямого подключения только при явном выборе пользователя.

## 9. Надёжность и тестирование

В проекте предусмотреть автоматические тесты, включая следующие сценарии:

| Сценарий                        | Ожидаемый результат                                            |
| ------------------------------- | -------------------------------------------------------------- |
| Один сервер недоступен          | Исключение из нового распределения                             |
| Все серверы недоступны          | Понятное состояние ошибки, выбранная политика Fail Open/Closed |
| Сервер восстановился            | Контролируемое возвращение в пул                               |
| Подписка временно не отвечает   | Использование последней валидной конфигурации                  |
| Повреждённая конфигурация       | Отказ от применения, сохранение рабочей версии                 |
| Аварийное завершение приложения | Восстановление или безопасное завершение сетевого режима       |
| Одновременно 500 соединений     | Без deadlock, утечек и неконтролируемого роста памяти          |
| Перезапуск Mihomo               | Восстановление управления и актуального состояния              |
| Изменение подписки              | Атомарное применение нового списка узлов                       |

### Критерии приёмки MVP

- Импорт подписки минимум с 10 рабочими VLESS-узлами.
- В режиме `round-robin` зафиксирован трафик через минимум два различных сервера при достаточном количестве новых соединений.
- После отказа одного сервера новые соединения успешно направляются через доступные узлы.
- Приложение сохраняет подписки и выбранные режимы после перезапуска.
- Системный прокси корректно восстанавливается.
- В интерфейсе отображаются фактические соединения и объём трафика.
- Приложение не заявляет об объединении пропускной способности отдельного соединения без поддержки bonding.

## 10. Этапы разработки

Этап 1 — рабочий MVP

Rust + EvertyUI, импорт подписок, запуск Mihomo, управление подключением, автоматическая диагностика, Load Balance и System Proxy.

Этап 2 — интеллектуальная маршрутизация

Smart Balance, фильтры узлов, история качества, гистерезис, приоритеты серверов и расширенная телеметрия.

Этап 3 — полноценная сетевая интеграция

TUN, обработка DNS/IPv6, аварийное восстановление, Fail Closed, автозапуск и установщик Windows.

Этап 4 — экспериментальный Multipath

Исследование собственного bonding-протокола с сервером-агрегатором, сегментацией данных, управлением порядком доставки и восстановлением потерь.

## 11. Что принципиально не входит в первую версию

Полноценное объединение нескольких VLESS-серверов для ускорения одного TCP-потока — отдельная большая задача. Разделение соединений между узлами не эквивалентно многопутевой передаче одного соединения.

Поэтому сначала реализуем проверяемый Smart Balance на Mihomo, а не будем усложнять первую версию самодельным протоколом.

Итоговая цель MVP: пользователь вставляет одну ссылку на подписку, нажимает «Подключиться», и приложение самостоятельно проверяет серверы, выбирает рабочий пул, распределяет новые соединения и автоматически реагирует на отказы.

Это уже полноценный самостоятельный программный продукт, который можно развивать в рамках Everty, не переписывая существующий VLESS-стек.

так же очень удобно должно быть добавлять в исключения домены или ip адреса.
